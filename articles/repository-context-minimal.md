AIは、その場で文章を書いたり、コードを直したり、調査を整理したりするのがかなり得意になりました。

一方で、仕事が数日、数週間と続くと、別の問題が出てきます。

- 前回どこまで進めたか分からない
- 何を正式な判断として採用したか分からない
- どのファイルが正本なのか分からない
- 別のチャットへ移ると、説明をやり直す
- AIが前の会話を覚えていても、それが最新状態とは限らない

そこで私たちは、**チャットの外に「仕事を再開するための文脈」を置く**運用をしています。

この方法を、私たちは **Repository Context** と呼んでいます。

## 会話全文を保存することが目的ではない

Repository Contextは、巨大なプロンプトを作る方法ではありません。

大事なのは、AIと人間が後から次を確認できることです。

- このプロジェクトは何のためにあるか
- 何が正本か
- いまどこまで進んでいるか
- 何をすでに決めたか
- 何が未決か
- 何をしてはいけないか
- 次に何をするか

原稿、コード、データ、契約書、研究資料などの原本は、それぞれ適切な場所に置いたままで構いません。

Repository Contextは、それらを全部コピーするのではなく、**必要なときに正本へ戻れる現在地**を持たせます。

## 最初は4ファイルだけでいい

最小構成は次の4ファイルです。

```text
AGENTS.md
REPOSITORY_CONTEXT.md
NEXT.md
HISTORY.md
```

これを既存プロジェクトのルート、または新しいGit Repositoryのルートへ置きます。

### AGENTS.md

AIに読ませる作業ルールです。

たとえば、

- 最初に何を読むか
- 何を勝手に変更してはいけないか
- 公開、削除、送信、デプロイに承認が必要か
- 作業後に何を更新するか

を書きます。

AIが高機能になるほど、「何ができるか」だけでなく、**どこまで任せるか**を書く価値が大きくなります。

### REPOSITORY_CONTEXT.md

プロジェクトの現在地です。

ここには、

- 目的
- 現在地
- 正本
- 重要なディレクトリ
- 採用済み判断
- 未決事項
- 禁止事項
- 次に読むもの

を書きます。

これはプロジェクトの説明書というより、**途中から参加した人間やAIが仕事へ復帰するための入口**です。

### NEXT.md

未処理と次アクションを書きます。

最初は欲張らず、次にやることを3件だけでも十分です。

```markdown
## いまやること

- [ ] Homeの原稿を直す
- [ ] 公開URLを確認する
- [ ] mobile表示を確認する
```

アイデアが増えたときに、その場ですべて着手せず「後でやること」「まだ始めないこと」に退避できるのも重要です。

### HISTORY.md

完了した作業と、採用済み判断を残します。

単に変更履歴を並べるだけでなく、

- なぜその判断にしたか
- 何をやらないことにしたか
- 後でどこを参照すべきか

が分かるようにします。

Gitのcommit履歴だけでは、「なぜ」を十分に残せないことがあります。HISTORYはその補助になります。

## 30分で始める

最初から立派な運用を作る必要はありません。

1. 既存プロジェクト、または新しいフォルダを用意する
2. 4ファイルを置く
3. `REPOSITORY_CONTEXT.md` に目的・正本・現在地を書く
4. `NEXT.md` に次の3件を書く
5. `HISTORY.md` に今日始めたことを書く
6. AIへ「まずAGENTS.mdとREPOSITORY_CONTEXT.mdを読んで」と伝える

これだけで始められます。

## 例：AIとWebサイトを作る

たとえば小さなWebサイトなら、次のように置けます。

```text
website-project/
├── AGENTS.md
├── REPOSITORY_CONTEXT.md
├── NEXT.md
├── HISTORY.md
├── site/
└── docs/
```

`REPOSITORY_CONTEXT.md` には、

- サイトの目的
- 公開URL
- 原稿の正本
- デザイン方針
- 公開してはいけない情報

を書きます。

次のチャットへ移ったときも、AIに「前回の会話を全部推測して」と頼むのではなく、Repositoryを読んで現在地を復元してもらいます。

## 特定のAIに依存しない

この方法はChatGPT専用ではありません。

Markdownを読める環境なら、Claude、Gemini、Codex、Cursor、Copilot、ローカルLLMなどでも使えます。

違うのは、

- AIがRepositoryを直接読めるか
- 人間がファイルを貼る必要があるか
- AIが直接編集できるか
- Gitの差分確認まで任せられるか

といった接続方法です。

Repository Contextそのものは、特定のAI製品の機能ではなく、**仕事の状態を外部に残す運用方法**です。

## すべてをContextへ詰め込まない

運用を続けると、今度はContext自体が巨大になります。

全文を全部残せば取りこぼしは減りますが、読むコストも増えます。

そのため、私たちは次のように分けています。

```text
原本
  ↓
必要な場所に保存

Repository Context
  ↓
目的・現在地・判断・参照先だけを保持

必要になったとき
  ↓
正本を読み直す
```

「何を残し、何を正本への参照にするか」は、Repository Contextを使い込んだ後に出てくる次のテーマです。
